@AGENTS.md

## Project

AutoGO is a Pakistani vehicle marketplace (buy, sell, rent cars and bikes; prices in PKR). It is a single Next.js 16 App Router app with MongoDB (Mongoose), NextAuth v5 (beta), UploadThing, Pusher, Gemini and Nodemailer. `documentation.md` is a long feature, model and API write-up. It is partly out of date (for example, it says the dev port is 3000), so check the code before relying on it.

## Commands

```bash
npm run dev          # dev server on http://localhost:3001
npm run build
npm run lint         # ESLint 9 flat config (eslint.config.mjs)
npx tsc --noEmit     # type check; CI runs this before tests, lint and build
npm test             # Vitest unit tests (src/**/*.test.ts), about a second
npm run make-admin   # tsx src/scripts/make-admin.ts: promotes ADMIN_EMAIL to role ADMIN
npm run reset-admin-key  # removes the admin access key set in the admin panel, so ADMIN_ACCESS_KEY works again
```

`tsconfig.json` excludes `.next/dev`: the Next 16 dev server sometimes writes its generated route types over themselves, which broke `npx tsc` while `npm run dev` was running. `next build` still type-checks its own `.next/types`.

Unit tests use Vitest (`vitest.config.ts`, `@/` alias) and live in `src/lib/__tests__/`. They cover the client-safe logic that handles money and dates: booking days, clashes and late fees, payment tags, installment schedules, plan expiry and quota months, plates, CNICs and phone numbers. They never touch the database, so keep tested code free of model imports (that's why `digestText` lives in `src/lib/today.ts`). Add a test when changing any of those rules. CI (`.github/workflows/ci.yml`) runs `tsc --noEmit`, the tests, lint and build, then deploys to Vercel: previews for PRs and production on pushes to `main`. All env vars are required at build time. See the CI file for the full list (`DATABASE_URL`, `NEXTAUTH_SECRET`, Google OAuth, `UPLOADTHING_TOKEN`, `GEMINI_API_KEY`, the Pusher server and `NEXT_PUBLIC_` keys, the email credentials, `ADMIN_SECRET`, `ADMIN_EMAIL` and the VAPID push keys). `src/lib/mongodb.ts` throws at import time if `DATABASE_URL` is missing. `CRON_SECRET` (Vercel project env only, not needed to build) enables the daily cron; without it `/api/cron/daily` refuses every call. `NEXT_PUBLIC_SUPPORT_WHATSAPP` is optional. When it is unset, the WhatsApp contact buttons are hidden. Email goes through Gmail (`EMAIL_USER`/`EMAIL_PASS`, about 500 a day) unless the optional `SMTP_HOST` (and `SMTP_PORT`, default 587) points at a transactional service such as Amazon SES, Brevo or Resend, whose SMTP login then goes in `EMAIL_USER`/`EMAIL_PASS` (`src/lib/email.ts`).

`npm run lint` currently reports 4 known errors (in `business/onboarding`, `BookingsContent` and `MessagesContent`). Compare against that baseline instead of expecting a clean run. The React compiler lint rules are strict:
- `react-hooks/set-state-in-effect` flags `useEffect(() => { load(); })` when `load` sets state, even after an `await`. The workaround used in this repo is to write the loader as a `fetch().then(...)` chain or to call it via `queueMicrotask`.
- `react-hooks/immutability` flags functions used in an effect before they are declared.

## Architecture

**Routing (`src/app`)** uses three route groups, each with its own layout and `error.tsx`:
- `(main)`: the public site and user area (listings, sell, bookings, messages, saved, compare, dashboard, profile) plus `admin/*`.
- `(business)/business/*`: a dealer or organization console with its own sidebar layout and inline styles, separate from the main Navbar shell.
- `(auth)`: login and register.

`src/app/api/**/route.ts` holds the REST handlers that client components call with `fetch`. Vercel caps them at 30s (`vercel.json`).

**Auth.** `src/lib/auth.ts` exports `{ handlers, auth, signIn, signOut }` and uses Credentials (bcrypt) and Google providers with JWT sessions. `session.user.id` and `session.user.role` are added in the callbacks and typed in `src/types/next-auth.d.ts`. Google sign-in creates the `User` document on first login.
- Route protection lives in **`src/proxy.ts`**, which replaces `middleware.ts` in this Next version. It wraps `auth()`, guards the protected prefixes and `/admin` (role `ADMIN`), and skips `/api`. API routes must therefore call `await auth()` and return 401 themselves.
- Server pages can use `requireAuth()` and `requireAdmin()` from `src/lib/session.ts`.
- User roles are `USER`, `SELLER` and `ADMIN`. The JWT role is only set at sign-in, so `proxy.ts` sees a role change only after the user signs in again.
- **Admin access levels.** `User.adminAccess` is `FULL` or `READ_ONLY`. A missing value means `FULL`.
  - Admin API routes must use `requireAdminApi("read" | "write")` from `src/lib/adminAuth.ts`, not a session role check. It re-reads the role from the database, and `"write"` rejects view-only admins.
  - **Hidden admin sign-in.** There is no visible admin login. Typing `ADMIN_ACCESS_KEY` (env, 16+ characters, server-only) into the email field on `/login` (any value without "@") calls `POST /api/auth/admin-key`, which compares it in constant time (`src/lib/adminGate.ts`) and, if right, sets a signed httpOnly cookie (`am_admin_gate`, path `/api/auth`, 10 minutes) that reveals the Admin sign-in form; wrong keys get the same "Invalid email or password" and count toward `adminKey` (5 per 15 min per IP). The key never signs anyone in: the admin form uses the same credentials provider with `portal: "admin"`, and `authorize` requires the gate cookie, the bcrypt password and role `ADMIN` (non-admins get the generic error; failures count toward `adminLogin` per IP plus the normal login limits). That sign-in sets `token.adminPortal`/`session.user.adminPortal`, and only such sessions pass `proxy.ts` for `/admin` and `requireAdminApi`; an admin who signs in through the normal form is an ordinary user and the menus hide the Admin panel link. `DELETE /api/auth/admin-key` ("Back to user login") clears the cookie. The platform owner can change the key from the admin Overview (`components/admin/AdminKeySettings.tsx`, `GET`/`PUT /api/admin/access-key`: current password, 16–128 characters, no spaces or "@"; rate limit `adminKeyChange`; logged `settings.adminKey`). `src/lib/adminKey.ts` stores it as a salted scrypt hash in the `adminAccessKey` `SiteSetting`, and once set it replaces `ADMIN_ACCESS_KEY` (the env key stops working, so a leaked key is really retired). `npm run reset-admin-key` deletes the setting to fall back to the env key.
  - The `ADMIN_EMAIL` account (`isPlatformOwner`) can't be demoted, limited or deleted.
  - Admin pages hide actions through `useAdminAccess()` (`components/admin/AdminAccess.tsx`, which reads `/api/admin/me`).
- **Business roles** are separate: `Employee.role` is one of `OWNER`, `MANAGER`, `SALES` or `STAFF`, linked to an `Organization`.
  - The `Employee` record is the source of truth. Read it with `getMembership(userId)`.
  - Check permissions with `can(role, permission)`, defined in `src/lib/business.ts`. The permissions are `manageTeam`, `editCustomers`, `deleteCustomers`, `manageBookings`, `manageSales`, `manageDeals`, `replyReviews`, `manageMoney` (owner, manager), `viewPerformance` (owner, manager) and `viewActivity` (owner only).
  - **Team activity log.** Business mutations call `logBusinessAction({ userId, organizationId? }, action, { type, id, label }, { details, amount })` (`src/lib/businessLog.ts`; never throws, skips users without a business). Action labels are in client-safe `src/lib/businessActions.ts`. The owner reads it in Staff → Activity (`GET /api/business/activity`, filter by member and type) and can delete it there (`DELETE /api/business/activity`, `?olderThan=30|90` or everything; a `business.clearActivity` entry records the deletion, and Performance loses the deleted counts); Staff → Performance (`GET /api/business/performance`, this or last month in Pakistan time) counts it per member. A new business mutation must log.
  - **Money** (`/business/money`, `manageMoney`): Cash book, Expenses and Profit per vehicle over `LedgerEntry` (IN/OUT, categories in client-safe `src/lib/money.ts`). Owners and managers add entries by hand (`/api/business/money/entries`; only `MANUAL` ones can be deleted). Payments write `AUTO` entries through `recordPaymentChange`/`recordOut` (`src/lib/ledger.ts`): booking payments, sale payments, installments, deposit refunds, and a `PAYMENT_CORRECTION` when a payment is lowered, so new money flows should write them too. Profit per vehicle (`/api/business/money/profit`) is a listing's sale price plus completed rental income minus OUT entries linked to it.
  - **Suspension.** Admins suspend a business with `PATCH /api/admin/organizations/[id]` (`suspend` with a reason, or `reinstate`).
    - Suspending sets `Organization.isActive = false` and stores `suspension.listingIds`, the live listings it switched to `INACTIVE`, so reinstating restores exactly those. The owner is messaged in Messages.
    - Warnings are an optional earlier step: `action: "warn"` appends to `Organization.warnings` and messages the owner. `SuspensionGate` shows open warnings as a banner, and the owner or a manager acknowledges them with `PATCH /api/business/warnings`. Businesses created before warnings existed have no `warnings` array, so guard array-filter updates with `$elemMatch`.
    - While suspended, `getMembership` returns null, so business APIs refuse. The `(business)` layout's `SuspensionGate` locks every page except `/business/support`, and posting or reactivating listings is refused (`isUserBusinessSuspended`).
  - **IDs.** A business has its own ID (`Organization._id`) besides each member's account ID; both show as the last 6 characters through `UserIdBadge` (`kind="business"` labels it "Business ID", `kind="me"` "My ID"). The console shows the Business ID in the dashboard header, Business settings and the sidebar business menu (with My ID), and support messages and the support WhatsApp text include both. Admins find either in the Businesses tab search or Plan lookup.
  - Business users contact the team from `/business/support`, which calls `POST /api/support/message` with a topic from `src/lib/supportTopics.ts`. The message lands in the support admin's Messages inbox and works while suspended, so the business can appeal.
  - `/business/guide` is a step-by-step tutorial for every console page (Today and "+ New", Bookings, Sales, Customers, Money, Deals, Staff) in English and Urdu (Nastaliq font, RTL; the language choice is kept in `localStorage`). The dashboard header's Guide button and the sidebar link to it. Its text lives in `guide/GuideContent.tsx`, so update both languages when any of those pages' buttons, statuses or role permissions change.
  - **Follow-ups.** `FollowUp` (customer, `dueAt`, note, `doneAt`) reminders: added from a customer's More tray (`editCustomers`), listed at the top of Customers and in the dashboard's `DueFollowUpsCard` (`components/business/FollowUps.tsx`, `/api/business/followups`). Deleting a customer deletes theirs; deleting a business also removes its follow-ups, ledger and activity log.
  - **Console helpers.** The dashboard starts with `TodayCard` (`components/business/Today.tsx`, `/api/business/today`: booking requests, pickups, returns, deposits to settle, purchase requests, installments and follow-ups due now, overdue first; item shapes in client-safe `src/lib/today.ts`). Its links open Bookings and Sales with `?q=<BK-/SL- number>` already searched. `SetupChecklist` (owner and managers; `/api/business/checklist` works out each first step; Hide is kept per browser) sits at the bottom, below Quick actions.
  - The sidebar (`NAV_GROUPS` in `BusinessSidebar`) has two groups: "Manage" for the daily work (Dashboard, Inventory, Customers, Bookings, Sales, Deals, Money, Staff) and "Grow & help" (Promote, Reviews, Reports, Updates, Guide, Settings, Help & support); put a new console page in the group it fits.
  - The sidebar marks the current page with a small gradient dot on the left and a faint background (`bg-white/[0.07]`), hover is only a light tint, and its icons have no tiles. On phones and tablets (≤768px) the console has a bottom bar (Today, Bookings, Sales, Customers with their badges, and More, which opens the sidebar drawer), rendered by `BusinessSidebar`; the top bar carries the notifications bell.
  - Every console page has the floating "+ New" menu (`components/business/QuickNew.tsx`, rendered by the business layout, hidden on onboarding and printable pages). It offers only what the role can do, using the client-safe `src/lib/businessPermissions.ts` (re-exported by `src/lib/business.ts`). Pages open their form for it with `useQuickNew(kind, open)`, which handles both `?new=<kind>` and a press while already on the page.
  - Business routes must scope every query to `member.organizationId`. Customers can only be deleted by the owner, and only when their status is `SOLD` or `LOST` (`src/lib/customers.ts`).

**AutoGO Official channel.** Admins post announcements, updates and offers at `/admin/announcements` (`/api/admin/announcements`, `[id]` for edit, pin and delete; logged as `announcement.*`). `Announcement` holds kind, title, body, an optional button link (an AutoGO path or `https://` only, checked by `parseAnnouncement` in `src/lib/official.ts`), `pinned` and an optional `endsAt` for offers. Names and colours are in client-safe `src/lib/announcements.ts`.
- A business follows for its whole team: `Organization.followsOfficial`/`followedOfficialAt`. Owners pick it at registration (onboarding step 4, ticked by default; `followOfficial` on `POST /api/business/organizations`), and the owner or a manager (`manageTeam`) can follow or unfollow from Business → Updates or the dashboard card (`PATCH /api/business/official`).
- Every member can read `/business/updates` (`GET /api/business/official`; `?seen=1` sets `User.officialSeenAt`). Unread posts are those newer than both `officialSeenAt` and `followedOfficialAt`; the sidebar "Updates" badge reads `/api/business/official/count` through `useNotificationCounts` (`updates`). A new post pushes `new-notification` to every follower's `user-<id>` channel (`notifyFollowers`, 100 channels per Pusher call). No emails are sent.

**Error log.** Production errors are kept in MongoDB and shown at `/admin/errors` (sidebar badge: open errors seen in the last 24 hours), so problems are visible without an outside service.
- Server code reports with `reportError(label, error)` (`src/lib/errorLog.ts`), a drop-in for `console.error` that also records it; every API route and server lib uses it, so new code should too (not in client-safe files: it imports a model). `src/instrumentation.ts` (`onRequestError`) records uncaught errors in pages, routes and actions, skipping Next's own `NEXT_*` digests.
- The error screens (`ErrorState`, `global-error.tsx`) send browser-only crashes to `POST /api/errors` with `reportClientError` (`src/lib/clientErrors.ts`); errors with a digest were already recorded on the server, and stale-build errors are skipped. Limited by `clientErrors` per IP.
- `ErrorLog` groups occurrences by source, label and message with numbers and ids blanked (`fingerprint`), counting repeats; each instance writes the same error at most every 10 s. Writes run in `after()` inside a request, and are skipped during `next build` (`NEXT_PHASE`), where waiting for an unreachable database pushed pages past Next's 60 s limit and failed the build. Entries untouched for 30 days expire (TTL). Admins mark them Fixed (`PATCH /api/admin/errors/[id]`, logged `errors.resolve`; a new occurrence reopens it) and delete fixed ones (`DELETE /api/admin/errors`, logged `errors.clear`).
- `GET /api/health` pings the database for uptime monitors: 200 or 503, never error details. API errors must not send `String(error)` to the client.

**System usage.** `/admin/usage` (sidebar Monitor → System usage; badge = services at or past 80%) shows the database and UploadThing storage against their limits. `src/lib/systemUsage.ts` reads MongoDB's own `dbStats` and `$collStats` per collection (data + indexes count toward the limit, as Atlas measures shared tiers; `DB_STORAGE_LIMIT_MB`, default 512 for the free M0) and UploadThing's `UTApi.getUsageInfo()` (the account total against the plan's `limitBytes`, plus this app's share and file count). Both are read-only and saved for 10 minutes with `unstable_cache` (tag `SYSTEM_USAGE_TAG`), so the page and badge add no load; `GET /api/admin/usage` (`requireAdminApi("read")`, `?count=1` for the badge, `?refresh=1` reads now, rate limit `usageRefresh`) never sends keys or error details. Levels, sizes and wording are in client-safe, unit-tested `src/lib/usageMeter.ts` (amber from 80%, red from 95%). Gemini, email and Twilio usage are not tracked yet.

**Money transactions.** A payment and its cash book entry are written together with `moneyTransaction(async session => …)` (`src/lib/ledger.ts`): the booking payment and deposit routes, walk-in sale creation and every money action on `PATCH /api/business/sales/[id]`. Inside one, pass `{ session }` to the writes and to `recordPaymentChange`/`recordOut`, which then throw so the whole change rolls back (outside one they still never throw). MongoDB may retry the callback, so send messages and notifications after it. Atlas supports transactions; on a standalone local mongod it runs without a session. The booking payment route sets `amountPaid` with `findOneAndUpdate` and reads the old value in the same step, and `Purchase` has `optimisticConcurrency` on `amountPaid`, `installmentPlan` and `status`, so two people recording money at once get a 409 ("Someone else just changed this sale") instead of counting it twice. New money flows should use the same pattern.

**Daily cron.** `vercel.json` `crons` calls `GET /api/cron/daily` at 03:00 UTC (08:00 in Pakistan) with `Authorization: Bearer $CRON_SECRET`; it runs once per Pakistan day (rate limit `cronDaily`). `runDailyJobs` (`src/lib/dailyJobs.ts`) runs each job separately:
- `remindExpiringPlans`: an email (`sendPlanExpiringEmail`) and push to paid plans ending within `PLAN_REMINDER_DAYS` (3), at most 100 a run. `User.planReminderFor` is set to the end date before sending, so each period is reminded once and a renewal gets its own reminder.
- `sendMorningDigest`: one push per person ("Today at <business>: 2 returns due · 1 installment due") for pickups and returns (`manageBookings`), installments (`manageSales`) and follow-ups (`editCustomers`) due today or overdue, the same items as the Today card; private owners get their own pickups and returns. Suspended businesses are skipped.
A new scheduled task should be another job in `runDailyJobs` (Vercel's Hobby plan allows daily crons only), and must finish within the 30 s limit.

**Rate limits.** `src/lib/rateLimit.ts` counts requests in MongoDB (`RateLimit` model: one document per key with a count and `expiresAt`, deleted by a TTL index), so limits hold across serverless instances. It fails open if the database is unreachable.
- Windows start at the first counted request, not at a clock boundary (fixed clock windows let a sign-in lock lift minutes after it started). Limits with `lockout: true` (sign-in, account-delete passwords) lock for a full window from the moment the limit is reached.
- `RATE_LIMITS` holds every limit. API routes call `rateLimitResponse(name, userId, what)` right after the session check; it returns a 429 with `code: "RATE_LIMITED"` and `Retry-After`, or null.
- Sign-in (`authorize` in `src/lib/auth.ts`) counts only failures: 5 per email and 30 per IP in 15 minutes. Over the limit it throws `RateLimitedSignin` (code `rate_limited`), which the login page shows. Unknown emails still run a bcrypt compare (`DUMMY_HASH`), so the response time doesn't reveal which emails exist.
- Sign-up counts only successful sign-ups (10 per IP an hour). Account deletion counts wrong passwords. `vehicleImages` uploads count per file (paid Gemini checks). Per-IP limits are generous because Pakistani mobile networks share IPs.
- Forms lock their submit button with a countdown once refused (`useRateLock(action)` in `src/hooks/useRateLock.ts`: `lock.check(res, data)` after the fetch, `disabled={lock.locked}`, label `lock.text`). The lock is kept in `localStorage` per action and per account (`ratelock:<action>:<userId>`, or `guest` when signed out; not read while the session loads), so reloading doesn't unlock it and another account in the same browser isn't locked by it (it used to be per action only, so switching accounts carried the countdown over although the server counts per account). Refusals carry `retryAfter` seconds, and sign-in encodes them in the error code (`rate_limited_<sec>`). Wait wording is in client-safe `src/lib/waitText.ts` (unit-tested): `waitText` ("45 seconds" … "12 days", rounded up; re-exported by `rateLimit.ts`) and `countdownText` for the button ("14:32", "2h 05m", "12 days"). Sign-in and account deletion refuse on the failure that reaches the limit, so the button locks at once. New rate-limited forms should use the hook.
- Covered: messages, support and upgrade requests, badge requests, reviews, bookings and deal bookings, purchase requests, saved searches and AI inspection. A new endpoint that sends messages, emails or paid AI calls needs a limit.

**Data.** Call `connectDB()` from `src/lib/mongodb.ts` before any query. It caches the connection on `global` for hot reload and serverless, with `maxPoolSize: 10` per instance so many serverless instances can't exhaust the cluster's connection limit. A failed connect clears the cached promise so the next request retries (a cached rejection used to break every page until restart). A request waits at most 10 s for the connection, DNS lookup included (`CONNECT_TIMEOUT_MS`; `serverSelectionTimeoutMS` doesn't cover the `mongodb+srv` lookup, which can hang far longer); an attempt that outlives a request keeps running and is reused if it succeeds. This keeps API routes under Vercel's 30 s cap during an outage and lets `next build` finish when the database is unreachable (pages that read it at build time, such as the home page and the sitemap, catch the error and render without data until they revalidate). Models in `src/models/` are registered with `defineModel(name, schema)` (`src/models/defineModel.ts`). In production it reuses the cached model. In development it replaces the cached model only when the schema's fields changed (it compares a fingerprint), so schema edits apply on hot reload. Replacing a model on every reload made routes that still held the old model hang with "buffering timed out". Use it for new models instead of `mongoose.models.X || mongoose.model(...)`.
- Business inventory is not owned by the organization directly. It is the listings whose `sellerId` is any organization member; see `getInventorySellerIds` in `src/lib/business.ts`.

**Plans and limits.** `src/lib/plans.ts` is the single source for plan names, prices and limits: `FREE`, `STARTER` ("Premium"), `PRO` ("Premium Plus") and `UNLIMITED`. A `null` limit means unlimited. The file is client-safe, and all UI text reads its numbers from it.
- The plan lives on the **user** (`User.plan`, `planExpiresAt`, `planSource`). Business members inherit the owner's plan, and `Organization.plan` is a legacy field that is no longer read.
- `src/lib/subscription.ts` provides `getSubscription`, `getUsage` and `checkPlanLimit(userId, "listings" | "staff" | "customers")`.
  - It is enforced server-side in `POST /api/listings`, `POST /api/business/deals` and the staff and customer POST routes.
  - When the limit is reached, those routes return 403 with `code: "PLAN_LIMIT_REACHED"`.
  - **The listing limit is a monthly quota shared by listings and deals** (there is no separate deal limit). Every listing or deal created in the calendar month (Pakistan time, see `quotaMonthStart`/`quotaResetsAt` in `plans.ts`) counts, even after it is deleted.
    - `POST /api/listings` and `POST /api/business/deals` check `checkPlanLimit(userId, "listings")` and write a `ListingLog` entry (`listingId` or `dealId`) that is never removed.
    - `getUsage` counts this month's log entries for the whole team, plus any listings or deals from this month that have no log entry yet.
    - Re-activating or re-tagging an existing listing doesn't use quota. `/api/subscription` returns `listingsResetAt`.
  - Staff counts include the owner.
- Clients read `/api/subscription` through `useSubscription()` (`components/subscription/`).
- There is no payment integration (the unused Stripe packages and `Payment` model were removed; Stripe doesn't serve Pakistani merchants). Admins activate plans through `PATCH /api/admin/users/[id]/plan` (`PlanGiftDialog`), and users ask for one through `POST /api/support/upgrade-request`.
- **Every paid plan ends.** Plans run in 30-day periods (`PLAN_PERIOD_DAYS`, `addPlanPeriods` in `plans.ts`), and there is no "no end date".
  - `source: "PAID"` gives one period. If the same plan is still running (paid, gifted or a trial), the new 30 days are added to the time left.
  - Gifts (`ADMIN_GRANT`) last 1, 3, 6 or 12 periods. The trial lasts `TRIAL_MONTHS` periods.
  - Once `planExpiresAt` passes, `effectivePlanId` treats the account as Free until the plan is bought again. `/api/subscription` returns `planDaysLeft`.
- `User.planSource` is `PAID`, `ADMIN_GRANT` (a gift) or `TRIAL`. Use `isFreeGrant()` from `src/lib/plans.ts` for "an admin can revoke this".
- Each account gets one free trial (`TRIAL_MONTHS` long), started with `trial: true` on the plan route. `User.trialUsedAt` is set atomically and never cleared, so revoking a trial doesn't allow another.
- The admin dashboard's **Plan lookup** box (`components/admin/PlanLookup.tsx`, `/api/admin/plans/lookup`) searches by name, email, business name, or full or short ID.
  - That request posts a chat `Message` to the support admin (`getSupportAdmin` in `src/lib/support.ts`).

**Bookings.**
- A `Booking` belongs to a `Rental`, which belongs to a listing. It has no organization field, so business bookings are the ones on `getBusinessRentals(userId)`, meaning rentals owned by any member.
- `source: "WALK_IN"` bookings have no `renterId`. They store customer details in `walkIn` instead, so treat `renterId` as optional. The personal `/api/bookings?role=owner` list excludes them.
- The business console (`/business/bookings`, `/api/business/bookings`) creates walk-ins and enforces the status flow in `src/lib/bookings.ts`: PENDING → CONFIRMED → ACTIVE (handed over) → COMPLETED, with cancellation before handover.
- Business booking cards are compact: the next step (Confirm, Hand over or Mark returned) plus Slip, WhatsApp and a More tray (payment, handover details, cancel or remove, vehicle tag). The list is two columns on `xl` screens.
- `/business/bookings/[id]/slip` is the printable slip. It is a fixed A4-width sheet (`SHEET_WIDTH` = 703px, the printable width with 12 mm margins) that prints on one page; narrower screens show the same sheet scaled down with CSS `zoom`, so phones see the whole page without scrolling. Its business signature carries a horizontal "AutoGO-Pak" ink stamp (`components/bookings/AutoGOStamp.tsx`, an SVG with a fixed ink colour) showing the business name and the confirmed date. `/business/rentals` redirects to `/business/bookings`.
- **Walk-ins for unlisted vehicles.** The New booking dialog has an "Other vehicle (not listed on AutoGO)" option (picker value `other`). The business types in the vehicle, daily rate, deposit and an optional plate.
  - Such a booking has no `rentalId` or `dealId`. It stores `offListVehicle` and carries the business in `Booking.organizationId`, which `businessBookingQuery`, stats, counts, `ensureBookingCustomer`, the handover route and review eligibility all check.
  - Clashes are only checked when a plate is given, using `samePlatePattern` (spaces and dashes are ignored).
  - New booking is always available, even when the business has no listed rental vehicles.
- **Booking dates** (`src/lib/bookings.ts`).
  - A return date may equal the pickup date (`validBookingDates`), and `rentalDays` charges at least one day, so 23 → 23 and 23 → 24 Oct are both one day.
  - A booking holds the vehicle or deal from pickup up to, but not including, the return day, and a same-day booking holds just that day. The return day is therefore free for the next pickup.
  - Every clash check (listing rentals, walk-ins, deal bookings) must use `bookingClashQuery(start, end)`.
- **Handover details: number plate and renter CNIC.**
  - `Booking.plateNumber` and `Booking.renterCnic` are recorded at handover. `Rental.plateNumber` remembers the last plate to prefill the next one. Walk-ins may also carry `walkIn.cnic`, so read the CNIC with `bookingCnic(b)`.
  - In the business console, "Hand over" opens `HandoverDialog` (`components/bookings/`) and sends `{ status: "ACTIVE", plateNumber, cnic }`. The business route requires both for that move.
  - Personal owners add or correct both with `PATCH /api/bookings/[id]/handover`. Business members with `manageBookings` can use that route for business vehicles too.
  - `normalizePlate`, `normalizeCnic` and `formatCnicInput` are in `src/lib/plates.ts`. Cards show both values with `HandoverDetails`, and both slips print them.
- **Return time and late fees** (`src/lib/bookings.ts`).
  - At handover the business must set `Booking.dueBackAt`, the exact return time. `HandoverDialog` (`askReturnTime`) prefills it as the booked days counted as 24-hour periods from now. While the vehicle is out it can be corrected through `PATCH /api/bookings/[id]/handover` (`dueBackAt`).
  - "Mark returned" opens `ReturnDialog`, which sends `{ status: "COMPLETED", returnedAt }`. The route stores `returnedAt`, `lateDays` and `lateFee` from `lateCharge`.
  - The rule: up to `LATE_GRACE_MINUTES` (60) late is free; after that every started 24 hours (each with the same grace) is one extra day at the normal `bookingDailyRate` (rent ÷ days booked). `LATE_RULE_TEXT` is the wording shown to owners and renters.
  - Bookings handed over before this existed have no `dueBackAt` and are never charged. Overdue uses `dueBackAt`, falling back to `endDate`.
  - The late fee shows on business and renter cards, both slips, and counts toward business rental revenue (`stats`).
- **Condition checklist.** Handover (`HandoverDialog` with `askCondition`) and return (`ReturnDialog`) record optional `Booking.checkOut`/`checkIn` (odometer, fuel level, notes, up to 6 photos from the `checkPhotos` UploadThing endpoint, which has no AI check). `parseCheck` and `kmDriven` are in client-safe `src/lib/checklist.ts`; the return odometer can't be below the handover one. Return can add `extraCharges` with a required `extraChargesNote` (fuel, damage, extra km); they are part of `amountDue` and every booking total.
- **Security deposit.** After return (or cancellation) the owner settles it with `PATCH /api/bookings/[id]/deposit` (`{ refunded, note }`, note required when any is kept), through `DepositDialog`/`DepositTag`. `depositState` reads `depositRefunded`/`depositSettledAt`. It can be corrected later; the cash book records the difference.
- **Calendar.** `/business/bookings` has a List/Calendar switch: `components/bookings/BookingCalendar.tsx` shows one row per rental, rent deal or off-list vehicle with a bar per booking over the days it holds the vehicle.
- **Payment tag.** The owner records what the renter has paid with the Payment button or the tag (`PaymentDialog`/`PaymentTag` in `components/bookings/PaymentTag.tsx`), which calls `PATCH /api/bookings/[id]/payment` with `{ status: "PENDING" | "PARTIAL" | "PAID", amountPaid? }`.
  - Only `Booking.amountPaid` is stored. The tag comes from `paymentState` in `src/lib/payments.ts`, which compares it with `amountDue` (rent + deposit + late fee), so a paid booking shows "Partly paid" again if a late fee is added afterwards.
  - The route and the handover route share the permission check `loadOwnedBooking` (`src/lib/bookingAccess.ts`): the rental's owner, or business members with `manageBookings`.
  - Business cards and the personal "received" tab can change it; renters see it read-only. Both slips print the tag, the amount paid and the balance.
- Every booking is linked to a CRM `Customer` of the renting business through `ensureBookingCustomer` (`src/lib/customerSync.ts`). It matches by `Customer.userId`, then by phone digits, then by email. It creates the customer only within the plan's customer limit.
- The customer link is set when an online or walk-in booking is created. `GET /api/business/customers` back-fills older bookings via `syncBookingCustomers`.

**Direct purchases (sales).** Buyers can ask to buy a vehicle a **business** is selling; private sellers keep Call/WhatsApp/Message only.
- A `Purchase` (`src/models/Purchase.ts`) links a buyer to the selling `organizationId` and a `listingId` (an ACTIVE `SALE`/`BOTH` listing by a member) or `dealId` (a live non-RENT deal), or neither for a walk-in sale of an unlisted vehicle. It stores a `vehicle` snapshot and the `buyer` details, so records survive edits and deletes.
- Flow: `REQUESTED` → `ACCEPTED` (price agreed) → `COMPLETED` (sold), or `DECLINED`/`CANCELLED`. `src/lib/purchases.ts` (client-safe) has the labels, `purchaseNumber` (`SL-XXXXXX`), `salePrice` (agreed, else offer, else asking) and `purchasePayment`; payments share `paymentStateFor` with bookings.
- Buyers use `BuyRequestButton` (`components/purchases/`) on the listing page (business listings for sale, hidden from the seller's own team) and on SALE deal pages, which calls `POST /api/purchases` (phone, optional CNIC, offer and message). One open request per buyer per vehicle, at most 10 open. The listing's seller gets a chat message. Buyers follow them at `/purchases` (cancel while open) with a slip at `/purchases/[id]/slip`.
- The business handles them at `/business/sales` (sidebar "Sales"; permission `manageSales` = owner, manager, sales): Accept (agreed price), Decline (reason), Mark as sold (final price, plate, amount paid), payment tag, New sale (walk-in, sold now or agreed), CSV export, and stats. The API is `/api/business/sales` and `PATCH /api/business/sales/[id]` with `action`. Accept, decline and sold message the buyer.
- **Installments (qist).** `PATCH /api/business/sales/[id]` actions `installments` (`downPayment`, `months` ≤ 60, `firstDue`), `removeInstallments` (only with nothing paid), `payInstallment`/`unpayInstallment` (`index`). The plan lives on `Purchase.installmentPlan`; paying one adds to `amountPaid` and the cash book. `buildSchedule`/`installmentSummary` are in client-safe `src/lib/installments.ts`; the UI is `components/sales/Installments.tsx`, with a printable schedule at `/business/sales/[id]/installments`. Buyers see the plan line in My purchases.
- `finishSale` (`src/lib/saleItems.ts`) tags the listing Sold (or pauses the deal), declines other open requests for that vehicle and clears the page caches. `ensurePurchaseCustomer` links the buyer to the business's CRM (NEGOTIATING, then SOLD when sold).
- The sale slip (`components/sales/SaleSlip.tsx`) is the same one-page A4 sheet as the booking slip, with the stamp (`caption="SALE COMPLETED"`) once sold.
- **Removing records.** Finished purchases (`REMOVABLE_PURCHASE_STATUSES`: sold, declined, cancelled) can be removed from either side; open ones must be declined or cancelled first. `DELETE /api/business/sales/[id]` (`manageSales`; a sold record needs `manageMoney` and no balance owed) sets `deletedByBusiness`, `DELETE /api/purchases/[id]` sets `deletedByBuyer`, and every list, count and loader skips its own side's removed records. An unsold record is deleted once no one still sees it (walk-ins straight away); a sold one is only ever hidden, because profit per vehicle and the cash book still count it. Logged as `sale.remove`.
- Badge counts come from `/api/purchases/count` (`purchases` for buyers' unseen updates, `sales` for new requests). Deleting a buyer's account cancels their open requests and unlinks them; deleting a business deletes its sales.

**Verified badge.** A PKR 500/month add-on for businesses, separate from plans. `VERIFIED_BADGE`, `isVerified` and `badgeState` are in `src/lib/plans.ts`.
- It is stored on `Organization.verification`. `verifiedAt`/`expiresAt`/`source` (`PAID` or `ADMIN_GRANT`) record the grant. `requestedAt` marks an open request from the owner, and `rejectedAt`/`rejectionReason` record the last refusal. Always check with `isVerified()`, because an expired badge keeps its `verifiedAt`.
- The owner requests it from the pricing page (`VerifiedBadgeOffer`, which calls `POST /api/business/verification`). That records `requestedAt` and messages the support admin.
- Admins handle it from the Badge button in the Businesses tab (`VerifyBadgeDialog`), which calls `PATCH /api/admin/organizations/[id]` with `verify`, `rejectVerification` or `unverify`. Renewing adds the months to the time left.
- Public pages show `components/VerifiedBadge.tsx`, and so does the console beside the business name (sidebar business card and its menu, the phone top bar, the dashboard header), from `verified` on `GET /api/business/organizations`. Unverified businesses use a building icon so only verified ones show a tick. Public queries select only `verification.verifiedAt verification.expiresAt`. `getSellerBusinesses` returns `verified`.

**Sponsored ads.** Businesses pay to show their business page, a live deal or an active vehicle to buyers: in the home page's "Featured businesses" row (the first section under the hero, above Recently viewed) and between Browse results. Prices and limits are `SPONSORED_AD` in `plans.ts`: two tiers (`AdTier`, `AD_TIER_LABEL`), Standard PKR 1,000 and Top PKR 2,500 a week (`adPrice(weeks, tier)`), 1/2/4 weeks, `slotsShown` (8) cards per row, `topPerCity` (2), `browseEvery` (12).
- **City first, then rotation.** An `Ad` stores the business's `city` (`Organization.city` when it asked; none means shown everywhere) and its `tier`. `getSponsored({ city, make, type, limit })` (`src/lib/sponsored.ts`) takes every running ad, keeps the ones matching the Browse `make` and sale/rent `type`, and orders them: Top ads in the visitor's city, then that city's Standard ads in a weighted random order (Verified businesses weigh 1.5), then other cities' ads to fill. It picks again on every call, so ads rotate; there is no global cap, any number of Standard ads can run and each gets a share of views (`standardShare(standardAds, topAds)` in `plans.ts`, unit-tested: "about 1 in N visits"). Cities compare with `sameCity`/`cityQuery` (case and spaces ignored).
- **Where they show.** `GET /api/sponsored?city&make&type&limit` (public, CDN-cached `PUBLIC_CACHE_SECONDS`, so a city's rotation changes about once a minute). The running ads themselves (`loadCandidates`) are cached once for everyone with `unstable_cache` (tag `SPONSORED_TAG`, cleared by `invalidateSponsored()` when an admin approves or stops an ad, and by `invalidateBusinessSlug` whenever a business's name, logo, badge or suspension changes), so made-up query strings can't turn into database reads; only filtering and shuffling run per call. The home page server-renders an All-Pakistan set into `SponsoredSection` (`components/home/`), which swaps in the visitor's city (the Browse city picker, `MY_CITY_KEY`). Browse fetches ads for its city, make and type and shows `SponsoredCard` (`components/home/SponsoredRow.tsx`, `layout="grid"|"list"`) after the 4th vehicle, then after every `browseEvery`, each ad once. The home section heading lives in `components/home/SectionHeader.tsx`.
- **Views and taps.** Cards count a view once half of them is on screen and a tap on click (`trackAds` in client-only `src/lib/adTrack.ts`: once per ad per event per session, `sendBeacon`) to `POST /api/sponsored/track` (rate limit `adTrack` per IP, only running ads, always 204), which `$inc`s `Ad.views`/`Ad.taps`. The business sees them on its ads in Promote (with the tap rate), the admin on each ad.
- The owner or a manager (`promote` permission) asks at `/business/promote` (sidebar "Promote"): what to promote, Standard or Top, weeks and the payment reference (`POST /api/business/ads`, rate limit `support`, at most 5 waiting). The page shows the city's `reach` from `GET /api/business/ads` (`cityAdLoad`: Standard and Top ads running there over the coming week, so "about 1 in N visits"; `topFreeFrom` when both Top places are taken, from `topBlockedUntil`), or asks for a city in settings. It messages the support admin and logs `ad.request`; `DELETE /api/business/ads/[id]` cancels a waiting request.
- `Ad` (`src/models/Ad.ts`) is `REQUESTED` → `APPROVED` (with `startsAt`/`endsAt`), or `REJECTED`, `CANCELLED`, `STOPPED`. `adState` in client-safe `src/lib/ads.ts` turns approved ads into scheduled, running or ended by date.
- Admins handle them at `/admin/ads` ("Ad requests", sidebar badge from `GET /api/admin/ads?count=1`; each ad shows tier, city, views and taps): `PATCH /api/admin/ads/[id]` `approve` (optional start date; a Top ad is refused when `topPerCity` Top ads already overlap those dates in its city, naming the first free day; Standard ads are never refused for space), `reject` or `stop` (reason required). The business is messaged, the action logged (`ad.*`), and `/` revalidated.
- **Clearing history.** Finished ads (ended, refused, cancelled, stopped; `finishedAdFilter`) can be cleared from either side: `DELETE /api/business/ads` (`promote`, logs `ad.clearHistory`) sets `hiddenByBusiness`, and `DELETE /api/admin/ads` (Past tab, write admins, logs `ad.clearHistory`) sets `hiddenByAdmin`. `clearAdHistory` (`src/lib/adHistory.ts`) deletes an ad once both sides have cleared it, so neither side's clear wipes the other's record. Waiting, upcoming and running ads can't be cleared.
- Cards (`SponsoredCard`): on Browse a thin gold border (`highlight`, `ring-[1.5px] ring-amber-300/80`; the owner chose it over a glow or tinted card, which looked loud; the home row, all ads, keeps the plain border because gold on every card looked funky), the photo (for a business page, the logo filling the photo area, with the Verified tick beside the shop name, then a caption such as "Car dealer · Lahore" and a short line from `Organization.description`, or a stock line for its type, `caption`/`blurb` in `sponsored.ts`) with a tilted gold "Sponsored" ribbon in the top-left corner (smaller on the list layout), title, price and a link to the business's shop page. Suspended businesses and deals or listings that are no longer live are skipped. Deleting a business deletes its ads. The pricing page's card ("Get Your Business Noticed", megaphone at the start of the heading) lists the benefits and both tiers, with a link to Promote. Area targeting (DHA, Gulberg…) is not built: it needs a structured area list per city.

**Payment details.** There is no payment gateway, so admins enter the account people pay into (account title, bank, IBAN, account number, JazzCash, EasyPaisa, a note) on the admin Overview (`components/admin/PaymentSettings.tsx`, `PUT /api/admin/payment-details`, stored as the `payment` `SiteSetting`, logged `settings.payment`). `GET /api/payment-details` is public. `PaymentDetailsCard` (`components/subscription/`, "How to pay" with copy buttons) shows it where people pay: the upgrade dialog, Business → Promote and Business → Help & support. The pricing page shows no account details: it has a Sponsored ads card (icon at the start of its heading, benefits, the Standard and Top prices from `SPONSORED_AD`, a link to Business → Promote) and "How payment works" as three `StepCards` (choose a plan, pay the team, an admin switches it on), and hides itself while nothing is set. Fields and `cleanPaymentDetails` are in client-safe `src/lib/paymentDetails.ts`.

**Reviews and deals.**
- Reviews belong to **businesses**, not individual sellers or listings. `BusinessReview` allows one review per user per organization, and the business can add a public `reply`.
- Only people who dealt with the business may review it (`canReviewBusiness` in `src/lib/reviews.ts`): they booked, messaged a member, or are a CRM customer. Members can't review their own business.
- `src/lib/reviews.ts` also provides `getBusinessRatings` and `getSellerBusinesses` (seller id → business, used to label listings "Business" or "Private seller").
- The public business page is `/dealers/[slug]` (`Organization.slug`), with its reviews API at `/api/businesses/[slug]/reviews`. Old `/biz/<slug>` links redirect there (`next.config.ts`). The business console has `/business/reviews` and `/business/deals`.
- The business picture is `Organization.logo`. The owner or a manager sets it in business settings (`BusinessProfileCard`, using the `profileImage` upload endpoint). `PATCH /api/business/organizations` only changes the fields it is sent, and accepts only UploadThing URLs (`isUploadedImageUrl` in `src/lib/uploadUrls.ts`). It shows on the dealer page, the listing "Listed by" box and the console sidebar, which reloads on the `ORG_UPDATED_EVENT` window event.
- **Deals are stand-alone offers, not discounts on listings.** A `Deal` has its own photos, vehicle details (make, model, year, condition, city and so on), a normal `price`, a percent or PKR discount, and `startsAt`/`endsAt`. Nothing has to be listed first, and listing pages show no deal pricing.
  - The owner or a manager (`manageDeals`) creates and edits deals at `/business/deals/new` and `/business/deals/[id]/edit`, using `components/business/DealForm.tsx`.
  - `parseDealInput` (`src/lib/dealInput.ts`) validates the input. Photos go through the same AI-checked `vehicleImages` upload as listings: each URL must have a `VehicleImage` record from a member of the business, or already be on the deal.
  - `dealState`, `dealPrice`, `dealLabel` and `MAX_DEAL_IMAGES` are in client-safe `src/lib/deals.ts`. Shared vehicle option lists are in `src/lib/vehicleOptions.ts`.
  - The public pages are `/deals` (filters for make, city and sort in the URL) and `/deals/[id]`. The business page and the home page's "Hot deals" strip show `components/deals/DealCard.tsx`. The card keeps one accent and light details like the Sponsored card: the photo carries only a very small tilted rose→orange "Deal" ribbon across the top-left corner (same corner and angle as Sponsored, one size smaller; no photo count) and "N cars" at the bottom right for convoys; the body is a one-line title, a modest price with a small grey "PKR", the old price struck through with the discount in rose (amounts in lakh, `offText`), a grey city and time-left row (rose only within 3 days; "2d left" on phones, `endsText` from `sm`), and from `sm` up the business under a hairline. Make, year and Sale/Rent are left to the deal page. All of them read through `src/lib/publicDeals.ts` (`getLiveDeals`, `getDealPage`), which hides deals of suspended businesses.
  - **Deal types.** `Deal.dealType` is `SALE` or `RENT`. Older deals have no type and count as sales (`isRentDeal`).
    - A RENT deal is a bookable package: `price` is per day for the whole package, `vehicleCount` is the number of cars (for example an event convoy), and `deposit` is optional.
    - Customers book rent deals at `/deals/[id]/book` (the shared `BookingForm` with `dealId`), which calls `POST /api/deals/[id]/book`. The pickup date must be on or before the deal's end, overlapping bookings are refused, and the business's own members can't book.
  - **Deal bookings** are ordinary `Booking`s with `dealId` set and no `rentalId`, so they go through the normal flow (confirm, handover with plate and CNIC, return, slip). They show a DEAL tag.
    - `src/lib/dealBookings.ts` (`businessBookingQuery`, `getOrgDealIds`, `DEAL_BOOKING_FIELDS`) includes them in business booking lists, booking details, stats, pending counts and review eligibility.
    - Walk-ins can be made for a rent deal: the picker value is `deal:<id>`.
    - `ensureBookingCustomer` takes the business from the deal. Never assume `booking.rentalId` exists.
- Admins see and disable deals at `/admin/deals`. `disabledByAdmin` can't be undone by the business.
- The old per-seller `Review` model and `/api/reviews` were removed. Their documents are left in the `reviews` collection but nothing reads them.

**Public caching (60 seconds).** `src/lib/pageCache.ts` sets `PUBLIC_CACHE_SECONDS` and has the tag helpers.
- The home page (`/`, `src/app/(main)/page.tsx`) uses `export const revalidate = 60`. There is no separate landing page any more: `/home` redirects permanently to `/` (`next.config.ts`), and every logo and "Back to marketplace" link goes to `/`. "How it works" and the pricing page's "How payment works" use `StepCards` (`components/ui/StepCards.tsx`, server-safe): numbered cards joined by still arrows (slate→sky) to the next card, pointing down on phones and across from `sm` (an animated spark was tried and removed). Its section headings are one plain title and a quiet "View all" (`SectionHeader`; no small coloured eyebrow labels above them); the lower sections (Why AutoGO, How it works, Browse by province) add a thin indigo→fuchsia line across (like `MenuGroupTitle`), while Browse by make through Available for rent pass `line={false}`. "Browse by make" (`components/BrandLogos.tsx`) is a grid of plain logos with the name under each (no tiles, no scrolling): two rows (7 logos on phones, 11 on tablets, 15 on desktops, hidden with CSS only) completed by a More tile that opens all of them, then Show less. Logos are 256px transparent PNGs in `public/brands` named after the make in lower case, and every make there must also be in `MAKES` (`src/lib/vehicleOptions.ts`, which Browse, Sell and the deal form read), or sellers can't pick it and its link finds nothing. Below "Available for rent" it shows `LiveStats` (`components/home/LiveStats.tsx`, a dark glow panel, "AutoGO in numbers"): active listings, for sale, for rent, businesses, registered users, live deals and cities from `getPublicStats` (`src/lib/publicStats.ts`, cached for a minute), which re-polls `GET /api/stats` every minute while the tab is visible.
- The listing page and the `/dealers/[slug]` page call `auth()`, so they render per request. They cache their visitor-independent database reads with `unstable_cache`, tagged `listing:<id>` and `business:<slug>`. `"use cache"` would need Cache Components, which this app doesn't enable.
  - Cached values are plain JSON, so ids and dates are strings. After a cache hit nothing has called `connectDB()`, so connect before any extra live query.
  - Viewer-specific parts stay live: the dealer page's own review and review eligibility.
- Deals are cached the same way: `deal:<id>` for a deal page and `deals` for every deal list. Every deal mutation calls `invalidateDeal`, which also clears the business page.
- Routes that change those pages expire the tags straight away with `invalidateListingAndSeller`, `invalidateBusinessPage` or `invalidateBusinessSlug`. These are listing create/edit/delete, admin listing changes, AI inspection, business settings, deals, reviews and replies, and admin business actions. A new mutation that changes what those pages show must call one of them.
- `GET /api/listings` (the public browse feed) sends `Cache-Control: public, s-maxage=60, stale-while-revalidate=60` for the CDN.
- Don't cache anything per user: dashboards, the business console, admin and messages.

**Deleting accounts.** Users delete their own account from Profile & settings (`components/profile/DeleteAccount.tsx`, `GET`/`DELETE /api/profile/account`). They must type their email, and their password if they have one.
- `checkAccountDeletion` (`src/lib/accountDeletion.ts`) blocks the delete when:
  - the account is the platform owner or an admin
  - the user still owns a business (delete it first in Business settings)
  - the user has confirmed or ongoing bookings, as renter or owner
- `deleteAccount` removes their listings, rentals, inspections, favourites, saved searches, messages, reviews and staff membership, plus their UploadThing files. Photos a business deal still uses are kept.
  - Pending bookings are cancelled. Bookings they made as a renter keep their name and phone in `walkIn` and lose `renterId`, and business pages fall back to those details.
  - CRM customers keep their records but lose the `userId` link.
- The admin user delete (`DELETE /api/admin/users/[id]`) uses the same cleanup, with `byAdmin` relaxing the admin and booking checks.
- Deleting a business (`DELETE /api/business/organizations`) also removes its deals and reviews.

**Deploy skew.** `next.config.ts` sets `deploymentId` from `NEXT_DEPLOYMENT_ID`/`VERCEL_DEPLOYMENT_ID`, so a page left open across a deploy does a full reload on its next navigation instead of loading missing chunks. As a safety net, `ErrorState` and `global-error.tsx` use `reloadForStaleBuild` (`src/lib/staleBuild.ts`) to reload once (at most every 30 s) on chunk-load or missing Server Action errors, and their "Try again" does a full reload for those.

**Security headers.** `next.config.ts` sends a Content-Security-Policy plus X-Frame-Options DENY, nosniff, HSTS, Referrer-Policy and Permissions-Policy on every route. The CSP allows only this site, UploadThing (`utfs.io`, `*.ufs.sh`, `*.uploadthing.com`), Pusher (`*.pusher.com`) and Google profile pictures; inline scripts are allowed (Next.js and the theme script), `unsafe-eval` only in development. When the browser starts using a new outside service, add its host to the CSP or it will be blocked.

**Forgot password.** `/forgot-password` calls `POST /api/auth/forgot-password`, which always gives the same answer (no account enumeration) and emails a one-time link (`sendPasswordResetEmail`). Only a SHA-256 hash of the token is stored on `User.resetTokenHash`, with `resetTokenExpires` one hour out. `/reset-password?token=` calls `POST /api/auth/reset-password` (min 6 characters, like sign-up), which clears the token and the email's sign-in lock, then the page signs the user in. Both are rate-limited (`passwordResetEmail`, `passwordResetIp`). The login page links to it.

**Reports.** Users report a listing, deal or business with `ReportButton` (`components/reports/`, on the listing page seller box, the deal page and the dealer page header; hidden for the item's own seller or team). It calls `POST /api/reports` (reasons in client-safe `src/lib/reports.ts`; one open report per user per item, own items refused, rate-limited `reports`). `Report` (`src/models/Report.ts`) keeps a `targetLabel` snapshot.
- Admins review them at `/admin/reports` (sidebar badge from `GET /api/admin/reports?count=1`) and close them with `PATCH /api/admin/reports/[id]` (`resolve` needs a note, `dismiss`; `alsoSimilar` closes the other open reports on the same item). Acting on the item itself (removing a listing, switching off a deal, warning or suspending a business) uses the existing admin pages.

**Admin activity log.** Every admin change calls `logAdminAction(gate.admin, action, target, details)` (`src/lib/adminLog.ts`), which writes an `AdminLog` (admin, action, target type/id/label snapshot, details) and never throws. Action names and their labels are in client-safe `src/lib/adminActions.ts`. `/admin/activity` (`GET /api/admin/activity`, filter by type, search, 50 per page) shows them. New admin mutations must log.
- Only the platform owner (`ADMIN_EMAIL`) can delete that history (`DELETE /api/admin/activity`, `?olderThan=30|90` or everything; the GET returns `canClear`). An `activity.clear` entry records each deletion.
- The admin listing PATCH only accepts `status` and `featured` (it used to pass the request body straight to the database).

**Phone verification.** Profile & settings has `PhoneVerification` (`components/profile/`): `POST /api/profile/phone/send` texts a 6-digit code to a Pakistani mobile (`normalizePkMobile` in client-safe `src/lib/phone.ts`), and `POST /api/profile/phone/verify` checks it (10 minutes, 5 tries; `PhoneOtp` stores only a hash). Success sets `User.verifiedPhone` (E.164) and `phoneVerifiedAt`; a number can be verified on only one account, and editing the profile phone clears it.
- SMS goes through Twilio's REST API (`src/lib/sms.ts`) when the optional `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and `TWILIO_FROM` are set. Without them, development prints the code in the server log and production refuses with "isn't available yet".
- The free trial needs a verified phone, and each phone gets one trial ever: `TrialClaim` (unique `phone`) is written when the trial starts and survives account deletion. Listing pages show a "Phone verified" tick for verified sellers.
- Rate limits: `phoneOtpUser` (3 per 15 min, lockout) and `phoneOtpNumber` (5 a day).

**Toasts.** `toast(message, { tone: "saved" | "removed" | "info", action? })` (`src/lib/toast.ts`) shows a short message at the bottom centre through `components/ui/Toaster.tsx`, mounted once in `Providers` (one at a time, slides up, gone after about 2.6 s, above `--am-bottom-bar`). **Realtime and notifications.** The server triggers Pusher events through `src/lib/pusher.ts`.
